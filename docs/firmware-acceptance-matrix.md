# 整机业务验收矩阵

日期：2026-11-12
状态：v1.8，122 行业务能力；75 行已覆盖，47 行排除，0 行待补。

## 1. 目的

这份表回答一个问题：`stategrid_meter` 产品的每一项业务能力，靠哪个
acceptance 用例证明，观察什么外部结果，还缺什么。单元测试证明函数正确，
本表只收端到端业务行为。基础设施、协议编解码细节和已明确排除的旧路径放在
第 2 节的 `X` 清单里。任何业务能力如果既不在明细表，也不在 `X` 清单，视为
矩阵遗漏，必须先补表再写用例。

被测对象是 Linux 整机固件孪生 `firmware_sim`。用例只能通过进程外部契约
观察：退出码、trace、EEPROM、flash，以及后续补的 UART、LCD、继电器捕获。
测试不读进程内变量，不以“函数被调用”代替业务结果。

## 2. 范围

范围内：

- 启动、复位、掉电恢复、参数初始化。
- RTC、日历、对时、时钟故障。
- 电能、需量、瞬时量、计量芯片状态。
- 费率、阶梯、结算、节假日。
- 分钟/小时/日/月/结算/瞬时冻结与补抄。
- 事件检测、记录、存储、读取、上报。
- 负荷控制、继电器、保护、本地按键。
- 显示、背光、显示映射。
- DL/T 645 与 DL/T 698.45 的读、写、控制、上报、安全。
- 安全模式、ESAM、密钥。
- 上报策略、列表、重试。
- EEPROM/flash 持久化、电能记录、事件/冻结存储。
- 升级与升级标志。

范围外，需在表中显式标 `X`：

- FIFO、list、bitarithm、arena、channel 等基础设施。
- A-XDR、帧头、校验和等纯编解码，除非它承载一个业务服务。
- bootloader 自身、板级驱动、SoC 启动代码。
- 仅存在于 `exclude` 列表、没有进入 IAR 源表的旧代码。
- 主机 `struct tm` 字节兼容，不作为 ARM 产品契约。

| X 范围 | 排除理由 |
|---|---|
| `infra/kernel` 的 FIFO、list、bitarithm | 基础设施，已有单元测试 |
| `infra/memory` 的 arena、byte_store | 基础设施，已有单元测试 |
| `infra/channel`、`components/services/channel` | 传输管道，不是产品业务 |
| A-XDR、645/698 帧编解码 | 由协议用例间接覆盖，不单独签收 |
| `infra/boot`、bootloader、启动汇编 | 不属于应用固件验收 |
| `targets/stategrid_meter/board`、`soc`、`driver_entry.c` | 板级/SoC 胶水，孪生用桩替代 |
| component.yaml `exclude` 的未构建源 | 不在产品二进制内 |
| 生产校准、厂测模式、`Rn8209Adj_K` | 工厂流程，不是现场业务 |
| 主机 `struct tm` 字节布局 | 主机工具链差异，不是 ARM 契约 |

## 3. 状态词汇

| 状态 | 含义 | 离开该状态的条件 |
|---|---|---|
| `A` 已覆盖 | 已有 acceptance 用例，判据是外部契约 | 保持绿色 |
| `B` 可补 | 现有观测面足够，只差用例 | 新增用例并进入 `A` |
| `C` 需观测 | 业务结果在进程内，缺少外部观测面 | 补 trace/文件/捕获面 |
| `D` 需激励 | 观测面够，但缺少输入模型，例如计量脉冲、UART 帧、停电 | 补可脚本化激励 |
| `E` 需规范 | 判据依赖产品规范、协议版本或业务决定 | 用户或规范给出可判定阈值 |
| `X` 排除 | 基础设施、纯编解码或明确不在本期范围 | 记录排除理由 |

`A` 只表示该行写明的行为被覆盖，不表示整个业务域完成。一个业务域只有在
所有 P0/P1 行都到 `A` 或 `X` 时才可签收。

## 4. 判据约定

- 每个用例必须有至少一个不依赖 trace 的外部产物，例如 EEPROM/flash 字节、
  退出码或报文捕获文件。trace 只能辅助定位。
- 期望值来自产品规范或已确认的旧版行为，不来自当前实现输出。
- 同一用例重复运行时，镜像必须从空白或固定种子开始，不能依赖上一次残留。
- 失败要区分设备失败（`failed`）和测试环境失败（`invalid`）。
- 时间相关用例固定初始时间，并显式跨过边界，不靠真实等待。

### 7.2 实施顺序

1. 先补观测面：UART/PLC/IR 收发捕获、继电器状态、LCD 段框、计量脉冲/电参、

2. 再补激励模型：RN8209 可脚本化、ESAM 可脚本化、掉电/上电可脚本化。

4. P1 补显示、上报、安全。
5. P2 补升级、看门狗、低功耗和诊断。

## 8. 签收规则

- 一个业务域签收，要求该域所有 P0 行到 `A` 或 `X`，P1 行到 `A` 或 `X`，
  P2 行有明确排期。全量“所有业务”签收要求 122 行全部到 `A` 或 `X`。
- 单元测试不能把一行从 `C/D/E` 提升到 `A`。必须有 acceptance 用例，且判据
  来自外部产物。
- `A` 行必须稳定通过，不能依赖上一次运行的镜像或真实等待。
- 新增业务能力先加矩阵行，再写用例。矩阵行没有 ID 的能力视为未纳入验收。
- 每次矩阵变更后重算第 5 节计数，保证总数和状态数对得上。
